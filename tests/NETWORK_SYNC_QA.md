# Фоновый импорт — проверка версии 1.0.1 (18.10.2026)

> Историческая проверка прежней версии. С 1.0.12 в сетевую `import/` размещаются только EXE и исходники; размещение шаблона отключено. См. `IMPORT_FOLDER_QA.md`.

## Стенд и границы

WordPress 7.1.3, PHP 8.4.26, MariaDB 11.8, Chromium / Playwright. Настоящие HTTP-запросы к WordPress, обычная админская сессия, тестовое WebDAV-хранилище с Basic Authentication и задержкой чтения 2,2 секунды. PHP HTTP-стенд работает с несколькими процессами, чтобы проверить гонки. Действующий пользовательский сайт, хостинг и NAS не подключались.

**103/103 теста плагина**, включая новые 89–103 (`test-network-sync.php`), **39/39 реальных HTTP/браузерных проверок** фонового обмена. Повторены прежние **26/26 браузерных проверок Windows-редактора** и **211 проверок импорта его XLSX / CSV / JSON**. EXE и все пять assets редактора побайтово прежние, редактор не пересобирался.

## Что проверялось

### Не зависеть от конструктора

До первого открытия страницы «Вопросы»:

1. При `DISABLE_WP_CRON=true` анонимный обычный GET главной страницы импортирует файл. В БД фиксируется источник `request`.
2. Следующий запрос в ту же минуту не повторяет импорт; следующий разрешённый тик импортирует изменённое содержимое.
3. Неизменённый файл обновляет отметку проверки, не отметку последней фактической загрузки.
4. На обычной Dashboard WordPress присутствует штатный heartbeat, но нет JS конструктора. Реальный вызов `wp.heartbeat.connectNow()` отправляет авторизованный AJAX; вопросы импортируются с источником `heartbeat`.
5. При полностью выключенном резервном watchdog обычный запрос ремонтирует старое часовое расписание, но не импортирует файл. Последующий **GET к голому `/wp-cron.php`** действительно запускает импорт и записывает `cron`; тест не подменён прямым PHP-вызовом воркера.

### Две последовательные минуты по реальному времени

Первый запуск WP-Cron читает CSV через реальный WebDAV с задержкой 2,2 секунды: завершение импорта позже старта проверки минимум на две целые секунды. После изменения CSV все страницы WordPress закрыты. Примерно через 61 секунду от **старта** первой проверки выполняется второй запрос к `/wp-cron.php`.

Между вызовами **не изменяются timestamps, хэш или расписание**. Второй запуск импортирует новую версию, а не пропускает «каждую вторую минуту» из-за времени завершения предыдущего чтения. В резервном режиме без внешних обращений PHP сам не запускается — этот тест сознательно использует внешний HTTP-вызов как источник часов.

### Конкурентность и очередь

- Восемь одновременных анонимных GET: одно чтение медленного NAS и ровно одно добавление вопросов.
- Восемь обычных ручных AJAX-импортов одновременно с настоящим WP-Cron: ровно одно добавление. Остальные активные/запоздавшие запросы сообщают `pending` либо неизменённый файл, без ложной ошибки.
- Дополнительный тест устаревших объектов `Quiz`: под lock перечитывается актуальный хэш.
- TTL-lock захватывается атомарно. Старый владелец не удаляет новый lock; потерявший lease процесс не пишет вопросы, аудит или курсор нового воркера. Перед записью lease продлевается и проверяется.
- Старая олимпиада за пределами последних 100 строк не теряется. Искусственный предел в один импорт за пакет доказывает справедливое продолжение трёх олимпиад и регистрацию события продолжения.
- Даже неработающее подключение для доставки редактора обрабатывается **после** проверки вопросов; при выключенном автоимпорте программа по-прежнему размещается плановым воркером.

**Уточнение:** штатные ручные действия теперь учитывают хэш. Внутренний вызов `auto_import_for_quiz(..., true)` по-прежнему означает намеренный принудительный повтор и не обещает идемпотентность последовательных явно принудительных операций.

### Админка и сохранность правок

- Живой статус: число вопросов в БД, последнее время проверки, источник, следующая допустимая проверка, ошибка чтения и готовый URL планировщика.
- Чистый открытый конструктор обновляет список после фоновых изменений без ручной перезагрузки и без цикла повторных reload.
- Изменённая несохранённая формулировка остаётся в DOM; вместо reload показывается уведомление. Отмена ручного подтверждения не теряет правки.
- Даже если пользователь начал ввод **после получения статуса, но до срабатывания отложенного reload**, таймер повторно проверяет состояние и не перезагружает страницу.
- Открытое окно импорта блокирует reload. Форма настроек не перезагружается и сохраняет несохранённый путь.
- Настройки и новый блок помещаются в экран 390 px без горизонтального переполнения. В Dashboard / настройках / конструкторе нет исключений JavaScript.
- Явный старый `hourly` остаётся часовым; для новой олимпиады выбрана минута. Старые минутные aliases совместимы. Ошибки NAS не удаляют существующие вопросы.

### Безопасность и отсутствие побочных изменений

- Статус AJAX: администратор с правильным nonce — 200; неверный nonce — 403; аноним — отказ; подписчик — 403.
- Heartbeat подписчика не содержит статус олимпиады. В ответах нет пароля сетевой папки и API-ключа.
- Сохранённое сообщение с HTML отображается как текст, не исполняется.
- Вопросы импортируются со скрытыми баллами по умолчанию.
- SHA-256 файлов вопросов, проектов `.wpoq`, ответов и пользовательских файлов на диске не меняется от проверок, за исключением сознательных правок CSV самим тестом.
- В сетевой `import/` продолжают размещаться только четыре собственных файла редактора; шаблоны сами не создаются.

## Повторение встроенного набора

**Только на тестовой копии WordPress** — набор создаёт/удаляет fixtures и вызывает настоящий общий воркер:

```bash
wp eval-file tests/test-suite.php --path=/путь/к/тестовому-wordpress
```

Браузерный/HTTP-стенд дополнительно требует локальный WebDAV с управляемой задержкой, многопроцессный PHP-сервер и Chromium. В установочный ZIP не входят тестовые серверы, пользователи, пароли, control-файлы, исходные CSV организатора, логи, дамп БД и снимки браузера. Финальный архив повторно установлен в WordPress; полный встроенный набор и реальный HTTP/браузерный сценарий выполняются для установленной сборки.

## Не обещаем невозможного

Без посетителей, heartbeat или внешнего/системного планировщика неактивный PHP-сайт не выполняет код по часам. Полностью кешированные обращения могут не достигать PHP. Ограниченные пакеты проверяют бюджет между заданиями; один долгий сетевой вызов или ограничения хостинга могут занять больше бюджета. Для независимой от посещений работы нужен реальный вызов WP-Cron извне раз в минуту; URL выводится в админке, новый анонимный API импорта не добавлен.
